# Mizan.ai — Format Conversion (Feature H) — Findings for Implementation

Scope confirmed: **DOCX → PDF and XLSX → PDF only** (v1). PDF → DOCX is explicitly
out of scope and does not work via this approach anyway — see below.

Everything below was verified by actually running `soffice --headless` against
real test files, not assumed from documentation. Findings are ready to hand to
Claude Code for implementation.

---

## Quick reference

| Conversion | Works? | Gotcha | Fix required |
|---|---|---|---|
| DOCX → PDF | Yes | Silent failure under concurrent calls | Unique LibreOffice profile per call |
| XLSX → PDF | Yes | Silent text truncation | Auto-fit column widths before converting |
| PDF → DOCX | **No** | Hard filter error, not just poor quality | Out of scope — use pdf2docx/Docling if ever needed |

## 1. DOCX → PDF: works, ~3.5s cold

```
soffice --headless --convert-to pdf --outdir <dir> <file>.docx
```

Confirmed clean output (headings, paragraphs) via `python-docx` round-trip test.
Return code 0, correct `sample.pdf` produced, ~3.5s on a cold LibreOffice start.

### Gotcha: concurrent calls silently fail

LibreOffice headless instances share a default user-profile lock. Ran 3
conversions simultaneously via `ThreadPoolExecutor`: **1 of 3 failed** —
return code 1, empty stdout, empty stderr, no output file written. No error
message at all, which makes this dangerous — it fails the exact way a flaky,
hard-to-diagnose production bug does.

**Required fix:** give every invocation its own isolated profile directory so
concurrent calls don't fight over the same lock:

```
soffice --headless -env:UserInstallation=file:///tmp/lo_profile_<uuid> \
    --convert-to pdf --outdir <dir> <file>.docx
```

Generate a fresh `<uuid>` (or tempfile-based path) per request, and clean up
the profile dir after the conversion completes. Do not reuse profile dirs
across concurrent requests. This must be implemented — not optional — since
Mizan.ai will have concurrent users hitting this tool.

## 2. XLSX → PDF: works, but silently truncates text by default

```
soffice --headless --convert-to pdf --outdir <dir> <file>.xlsx
```

Return code 0, PDF produced — but **content came out truncated** on first
test, with no error or warning of any kind:

```
Vendor Amount (SVAT (15%)Total
Al Rajhi Tr 1000 150 1150
Saudi Steel 5000 750 5750
```

"Amount (SAR)" → "Amount (S", "Al Rajhi Trading Co." → "Al Rajhi Tr".

### Root cause (confirmed)

In Excel/Calc, long cell text is allowed to *visually* overflow into an empty
neighboring cell on screen — but that's a display-only trick. Printing and
PDF export clip every cell strictly to its own column width, so any text that
only "fit" by overflowing gets silently cut off. The test workbook had
default column widths (13) with no print area and no fit-to-page scaling set
— this will be the default state of most workbooks generated by
`openpyxl`/report code unless explicitly handled.

### Required fix: auto-fit columns before conversion

Before calling `soffice`, widen each column to fit its longest cell value,
save to a temp copy, and convert *that* file:

```python
import openpyxl

wb = openpyxl.load_workbook(input_path)
ws = wb.active
for col_cells in ws.columns:
    length = max(len(str(c.value)) for c in col_cells if c.value is not None)
    col_letter = col_cells[0].column_letter
    ws.column_dimensions[col_letter].width = length + 2
wb.save(temp_path)
# convert temp_path, not the original
```

Confirmed this fully resolves the truncation — full text ("Amount (SAR)",
"Al Rajhi Trading Co.") came through correctly after auto-fit, verified via
`pdfplumber` text extraction on the output PDF.

Note: `page.extract_table()` (grid-line-based table detection) returned
`None` on this output since the test sheet has no cell borders — that's
expected and not a conversion bug, just extract_text() instead if verifying
programmatically. Don't rely on `extract_table()` for QA/testing on
borderless sheets.

## 3. PDF → DOCX: does not work via LibreOffice, out of scope anyway

Not needed for v1 (scope is DOCX/XLSX → PDF only), but documenting so nobody
assumes the reverse direction works the same way.

`soffice --headless --convert-to docx <file>.pdf` fails outright:

```
Error: no export filter for sample.docx found, aborting.
```

**Why:** LibreOffice imports PDFs as a **Draw document** (positioned shapes/
text boxes), not a flowing Writer document — regardless of what the original
PDF was. A Draw-loaded document has no Writer-format export filter available,
so DOCX and even ODT export fail immediately with a filter error. The only
formats it will export to are other Draw formats (e.g. ODG). This is a hard
limitation, not a quality problem — it doesn't produce a bad DOCX, it
produces no DOCX at all.

If PDF → DOCX is ever needed later: use `pdf2docx` (Python) or Docling
(already used elsewhere in this project) for text-based PDFs, with OCR as a
prerequisite step for scanned/image PDFs.

### UI note

Since PDF → DOCX isn't implemented (and won't work via LibreOffice the way
the other direction does), don't hide it entirely — show it in the UI as a
disabled/greyed-out option with a "coming soon" style label, same pattern
already used for the document-upload rail in the translation mockup. Clicking
it can show a brief in-context message rather than doing nothing. This signals
the feature is planned and actively being worked on, rather than making it
look like an oversight or a gap.

## 4. Architecture recommendation

- **Not** a standalone MCP server — that's disproportionate overhead for a
  single conversion function.
- Implement as a plain, framework-free Python function first (subprocess
  wrapper, easily unit-testable on its own), then wrap it as an MCP **tool**
  registered inside whichever MCP server already owns document output (same
  place `generate_report` lives — both are "produce a file in a requested
  format" operations in the same domain).
- CPU/IO-bound work, no GPU benefit — belongs on GCP infra alongside the
  FastAPI gateway / document-tools MCP server, **not** in `modal_app.py`
  alongside the GPU model classes.

## 5. Deployment requirement

Needs `libreoffice-writer` and `libreoffice-calc` installed in the container
image (confirmed these are the components actually invoked —
`writer_pdf_Export` filter for DOCX, `calc_pdf_Export` filter for XLSX). Full
`libreoffice` meta-package is unnecessary; writer + calc + core is enough for
this feature's scope.
